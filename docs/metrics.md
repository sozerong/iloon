# 운영 지표와 SLO — Illo-on

## 이 문서가 목표치를 정하는 방법

SLO 를 "이 정도면 괜찮다"로 정하면 아무것도 판정하지 못한다. 근거가 취향이기 때문이다.
여기서는 **목표치를 시스템에 이미 존재하는 제약에서 뽑아낸다.** 출처는 넷뿐이다.

| 근거 유형 | 뜻 | 예 |
|---|---|---|
| **A. 선언된 값** | 코드에 이미 박혀 있는 타임아웃·스케줄 | `execution_timeout=30min` |
| **B. 플랫폼 상수** | 내가 바꿀 수 없는 한계 | OpenSearch `http.max_content_length` 100MB |
| **C. 정합성** | 튜닝 대상이 아님. 1건이라도 틀리면 버그 | 응답 후 유실 0건 |
| **D. 대조군** | 같은 조건의 다른 선택지를 이겨야 함 | keyword 검색, LLM 없는 정렬 |

**목표치를 못 세우는 항목은 목표를 쓰지 않는다.** 근거 없는 숫자를 적는 것보다 낫다.

## SLO 현황

| 지표 | 목표 | 근거 | 실측 | 판정 |
|---|---|---|---|---|
| 분석 DAG 처리 시간 | ≤ 30분 | A | **74.2s** | ✅ 예산의 4.1% |
| 단일 색인 배치 규모 | ≥ 31,479건 | B | **50,000건** | ✅ |
| 색인 부분 실패 | 0건 | C | **0건** (50,000건) | ✅ |
| 수집 API 응답 후 유실 | 0건 | C | **0건** (20,000건) | ✅ |
| 스트리밍 적재 멱등성 | 재소비 후 행 증가 0 | C | **0** | ✅ |
| 검색 품질 Recall@3 | keyword 를 유의하게 초과 | D | **구별 불가** (p=0.736) | ❌ |
| 추천 정확도 | — | 목표 없음 | 측정 불가 | — |

미달 1건, 목표를 세울 수 없는 항목 1건. 아래에 각각의 근거를 편다.

## A. 선언된 값에서 나온 목표

### 분석 DAG 처리 시간 ≤ 30분

목표치를 내가 고르지 않았다. `dags/ai_analysis_dag.py` 에 이미 있다.

```python
"execution_timeout": timedelta(minutes=30),   # 태스크 공통
schedule_interval="0 2 * * *",                # 매일 02:00
max_active_runs=1
```

`execution_timeout` 은 **초과하면 태스크가 죽는 선**이다. 성능 목표가 아니라 실패 조건이라
논쟁의 여지가 없다. 학습 태스크만 45분으로 따로 열어 뒀다.

실측 **74.2초** (이벤트 244,839건 · 공고 2,000건 · 3회 p50) → 선언 예산의 **4.1%**.

상위 제약도 같이 본다.

| 제약 | 값 | 출처 |
|---|---|---|
| 다음 실행까지 | 24시간 | `schedule_interval` + `max_active_runs=1` |
| 상류 대기 상한 | 1시간 | `ExternalTaskSensor(timeout=60*60)` × 2 |
| 태스크 최악 소요 | 96분 | `(30분 + 3분) × 3` (`retries=2`) |

최악 경로(센서 1시간 대기 + 태스크 재시도 2회)를 밟아도 24시간 안에 끝난다.
**개선 전 126.3초도 이 예산 안이었다.** −41% 는 SLO 위반을 고친 게 아니라
여유를 늘린 것이고, 그렇게 적는 편이 정확하다.

## B. 플랫폼 상수에서 나온 목표

### 단일 색인 배치 ≥ 31,479건

OpenSearch `http.max_content_length` 기본값 **100MB** 는 내가 정한 값이 아니다.
이 선을 넘으면 느려지는 게 아니라 **한 건도 안 들어간다**(HTTP 413).

실측 문서 크기에서 상한이 계산된다.

```
30,000건 = 95.3 MB      →  문서 평균 3.25 KB
100 MB ÷ 3.25 KB        →  단일 요청 최대 31,479건
```

이 예측이 실측과 맞는지가 근거의 검증이다.

| 문서 수 | 예측 | 실측 |
|---|---|---|
| 30,000 | 통과 (< 31,479) | 2.963s 성공 |
| 35,000 | 실패 (> 31,479) | **HTTP 413, 0건** |

**계산한 상한 31,479가 관측된 성공/실패 사이에 들어간다.** 우연의 일치가 아니라
용량 한계가 바이트에서 온다는 증거다. 청킹 후 50,000건 정상 처리로 상한이 사라졌다.

### `chunk_size = 2000` 인 이유

"2,000 이후 개선이 멈춰서"는 절반만 맞다. 20,000건 3회 p50 은 이렇다.

| chunk_size | 200 | 500 | 1,000 | 2,000 | 5,000 |
|---|---|---|---|---|---|
| p50 | 6.685s | 3.487s | 2.534s | **2.386s** | 2.362s |

5,000 이 2,000 보다 0.024s **빠르다.** 회차 편차(2,000 의 실측 범위 2.327~2.418s,
폭 0.091s)보다 작으므로 구별할 수 없다. 속도로는 둘 중 하나를 못 고른다.

바이트를 보면 갈린다.

| chunk_size | 요청 크기 | 무엇이 실제로 제한하는가 |
|---|---|---|
| 2,000 | 6.4 MB | **건수** (`chunk_size`) |
| 3,147 | 10.0 MB | 경계 |
| 5,000 | 15.9 MB | **바이트** (`max_chunk_bytes=10MB`) |

**3,147건을 넘으면 `chunk_size` 는 장식이 된다.** 바이트 제한이 먼저 걸려
실제 요청은 3,147건으로 잘리기 때문이다. 설정값이 동작을 설명하지 못하는 상태다.

2,000 은 **속도가 포화된 뒤이면서 건수 제한이 여전히 지배하는 구간**이고,
요청 크기가 플랫폼 한계의 6.4% 라 문서가 커져도 여유가 있다. 그래서 2,000 이다.

> 문서가 지금의 1.6배(5.2KB)가 되면 2,000건도 10MB 를 넘어 바이트 제한으로 넘어간다.
> 그때는 사고가 아니라 청크가 작아지는 것으로 끝난다 — 이중 제한을 건 이유다.

## C. 정합성 — 목표가 0 인 것들

튜닝 대상이 아니다. **1건이라도 발생하면 성능 문제가 아니라 버그다.**

| 지표 | 왜 0 이어야 하는가 | 실측 |
|---|---|---|
| 응답 후 유실 | `BackgroundTasks` 는 응답 전송 후 실행되므로 그 사이 종료되면 사라진다. 클라이언트는 200 을 받았다 | 개선 전 **100건** → 후 **0건** (동시 20 · 20,000건 · 3회) |
| 색인 부분 실패 | HTTP 200 이어도 개별 항목은 실패할 수 있다. 세지 않으면 조용히 유실된다 | 50,000건 중 **0건** |
| 스트리밍 재소비 시 행 증가 | 체크포인트 유실 후 재소비는 정상 동작이다. 행이 늘면 집계가 틀린다 | **0** (유니크 인덱스 + `ON CONFLICT DO UPDATE`) |
| 배치 재실행 시 중복 | 멱등하지 않으면 백필이 불가능해진다 | 300행 → 재실행 → **300행** |

값이 0 인 지표는 "달성"이 아니라 **"아직 깨지지 않았다"** 로 읽어야 한다.
유실 0건은 동시 20 · 20,000건 조건에서의 결과이고, 부하가 커지면 다시 재야 한다.

## D. 대조군 — 목표가 다른 선택지인 것

### 검색 품질: neural 은 keyword 를 이겨야 한다 ❌

"Recall@3 0.7 이상" 같은 목표는 근거가 없다. 코퍼스 30건에서 0.7 이 무슨 의미인지
말할 수 없기 때문이다. **대조군을 목표로 삼으면 근거가 생긴다.**

neural 경로는 공짜가 아니다. ML 노드 배포 + `text_embedding` ingest pipeline +
`knn_vector` 384d 저장이 붙는다. **그 비용을 내고 keyword 를 못 이기면 넣을 이유가 없다.**

같은 쿼리 50개를 두 모드가 모두 처리했으므로 쌍체 검정이 가능하다.

```bash
python bench/search_significance.py
```

| | 값 |
|---|---|
| keyword Recall@3 | 0.5400 |
| neural Recall@3 | 0.5867 (+0.0467) |
| 부호검정 | 승 19 / 패 16 / 동점 15 → **p = 0.7359** |
| 쌍체 부트스트랩 95% CI | **−0.0533 ~ +0.1467** (0 포함) |

**판정: 구별 불가.** 평균은 올랐지만 쿼리 50개에서 0.047 은 문항 2.35개이고,
이긴 쿼리와 진 쿼리 수가 거의 같다(19 대 16).

평균만 봤으면 "neural 이 8.6% 개선"이라고 썼을 것이다. 쌍체로 보면 그 주장이 서지 않는다.
**백엔드/서버 카테고리에서는 neural 이 크게 졌다** — 방향도 일관되지 않는다.

- 코퍼스 30건은 IR 평가로 작다. 쿼리를 늘려도 코퍼스가 작으면 구간이 줄지 않는다
- 지금 상태로는 **neural 을 켤 근거가 없다**. 끄자는 게 아니라, 켤 근거를 아직 못 만들었다는 뜻이다

### 추천 정확도: 목표를 쓰지 않는다

`analysis_4` 는 `match_score = uniform(0.65, 0.98)` 로 생성된 값과
그와 **독립인** `apply_p` 를 비교한다. 두 변수가 독립이므로 상관이 나오면 그게 버그다.

목표치를 세우면 측정할 수 없는 대상에 숫자를 붙이는 셈이 된다. 그래서 비워 둔다.
근거: [ADR-0009](adr/0009-why-recommendation-accuracy-not-measured.md)

`view_id` 조인 팬아웃은 고쳤다(10.5% → 7.1%, 설계값 6.95%). 이제 "신호 없음"을
**올바르게** 보여 준다. 고치기 전에는 팬아웃 때문에 가짜 신호가 보였다.

## 목표를 세울 수 없는 것

정직하게 비워 둔 칸이다.

| 항목 | 왜 목표가 없는가 |
|---|---|
| 클라우드 비용 | 로컬 단일 노드다. 낼 수 있는 숫자가 없다 |
| 스트리밍 end-to-end 지연 | `trigger(30s)` + `window(30s)` + watermark 60s 로 **상한은 선언돼 있으나 실측하지 않았다** |
| 파이프라인 30일 성공률 | 연속 운영한 적이 없다. 3회 반복 측정이 전부다 |
| 데이터 신선도 | 수집원이 실제 채용 API 가 아니라 생성기다 |

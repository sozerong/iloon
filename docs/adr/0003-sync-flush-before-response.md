# ADR-0003. 임계치 플러시를 응답 전 동기 실행으로

- 상태: Accepted
- 날짜: 2026-08
- 프로젝트: Illo-on

## 맥락

이벤트 수집 API 는 이미 버퍼링돼 있었다 — 100건/5초 임계치, `asyncio.Lock`,
`lifespan` 관리, `CancelledError` 처리까지.

문제는 임계치 플러시가 `BackgroundTasks` 로 위임돼 있던 것이다.
버퍼에서는 이미 비워졌는데 디스크에는 아직 안 쓰인 구간이 생긴다.
그 사이 프로세스가 죽으면 그 100건은 어디에도 없다.
`lifespan` shutdown 은 이 백그라운드 태스크를 기다려주지 않는다.

## 먼저 확인한 것 — 저장은 병목이 아니다

방향을 정하기 전에 요청 처리 내부를 구간별로 쟀다 (n=2,000, 서버 내부 시간 p50).

| 구간 | p50 | 비중 |
|---|---|---|
| **검증 (Pydantic)** | **1.510 ms** | 약 93~95% |
| 직렬화 | 0.014 ms | 0.9% |
| **저장 (디스크)** | **0.002 ms** | 0.1% |

**"저장을 미뤄서 빠르게 만든다"는 전제가 이 코드에서는 이미 무의미했다.**
미루는 대가(유실 창)만 있고 얻는 게 없다.

## 유실 창이 실재하는가

ASGI 를 직접 호출해 클라이언트가 202 를 받는 그 순간(`http.response.body`)의
디스크 상태를 봤다.

| | 응답 시점 디스크 반영 |
|---|---|
| before | **0 / 100건** |
| after | 100 / 100건 |

before 는 `"flushed": 100` 이라고 응답해 놓고 디스크에는 한 건도 없다.

## 검토한 선택지

1. **lifespan shutdown 에서 백그라운드 태스크 추적·대기** — 태스크 집합을 들고 다녀야 하고,
   응답 이후 실행이라는 성질은 그대로다. 유실 창이 좁아질 뿐 사라지지 않는다.
2. **fsync 강제** — 유실 창과 무관하고 비용만 크다.
3. **요청 안에서 `await flush_to_disk()` (채택)** — 저장이 0.002 ms 라 미룰 이유가 없다.
   코드도 줄어든다.

## 결과 (동시 20 / 총 20,000건 / 3회)

| 지표 | before | after |
|---|---|---|
| p50 응답 시간 | 12.85 ms | 12.77 ms |
| p95 응답 시간 | 121.70 ms | 117.94 ms |
| 처리량 | 582 req/s | 598 req/s |
| **응답 시점 유실** | **100건** | **0건** |

**성능 차이는 없다.** 전부 회차 편차 안이다.
서버 내부 저장 p95 만 0.039 → 0.744 ms 로 올랐다 — 10요청마다 한 번 도는 플러시를
요청 안에서 기다리는 비용이고, 검증(1.5 ms)에 묻혀 end-to-end 에는 드러나지 않는다.

**얻은 것은 속도가 아니라 정확성이다.** "저장했다"는 응답이 실제로 저장을 의미하게 됐다.

## 검증

`tests/test_log_api.py` 4개 통과. 그중 "응답 시점 디스크 반영" 테스트는
**원본 코드에서 실패한다** — 회귀를 실제로 잡는다.
(TestClient 는 BackgroundTasks 를 기다려주기 때문에 ASGI 를 직접 호출해야 잡힌다)

## 남은 일

진짜 병목인 검증(1.5 ms)은 손대지 않았다. 줄이려면 `model_dump()` 대신 원본 dict 를
쓰거나 검증을 느슨하게 해야 하는데 둘 다 데이터 품질을 깎는 거래라 하지 않았다.
SIGKILL 로 죽으면 버퍼(최대 100건/5초)는 여전히 사라진다 — 없애려면 WAL 이 필요하다.

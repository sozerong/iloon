# ADR-0001. 조회 성격에 따른 저장소 분리

- 상태: Accepted
- 프로젝트: Illo-on

## 맥락

공고 데이터에 두 가지 조회가 붙는다.
1. 검색 — 자연어 질의로 관련 공고를 찾는다. 순위가 중요하고 정확한 일치는 덜 중요하다.
2. 정합성 조회 — 특정 id 의 공고를 가져오거나 집계 결과를 읽는다. 정확해야 하고 순위는 없다.

## 검토한 선택지

1. **PostgreSQL 단독** — `tsvector` 전문 검색으로 버틴다.
   기각: 한국어 형태소 분석이 약하고, 벡터 검색을 붙이려면 pgvector 를 얹어야 하는데
   그 시점에 "검색 엔진을 직접 만드는" 일이 된다.
2. **OpenSearch 단독** — 집계 결과까지 여기에 넣는다.
   기각: 분석 배치가 쓰는 `user_segments`·`job_popularity` 는 트랜잭션과 멱등 재적재가
   필요하다. `DELETE FROM` 후 INSERT 를 한 트랜잭션으로 묶는 게 관계형에서 훨씬 단순하다.
3. **둘 다 쓰고 역할을 나눈다 (채택)**

## 결정

- **OpenSearch**: 공고 문서 + `knn_vector`(384차원). 검색·추천 후보 추출 전용.
- **PostgreSQL**: 스트리밍 집계(`realtime_event_stats`), 배치 분석 결과
  (`user_segments`, `job_popularity`). 정합성이 필요한 쪽.

동기화는 하지 않는다. 공고 원본은 JSONL 이고 양쪽이 각자 그것을 읽어 적재한다.
한쪽이 실패해도 다른 쪽이 멈추지 않는다 (`job_importer.py` 는 OpenSearch 색인 실패를
로그만 남기고 계속 진행한다).

## 결과

- 검색 경로에서 관계형 조인이 사라졌다.
- 대신 **두 저장소가 어긋날 수 있다.** 공고가 PostgreSQL 에는 있고 OpenSearch 에는
  색인 실패로 없는 상태가 가능하다. 현재는 색인 성공 건수를 로그로만 남긴다.
  정합성 체크가 남은 과제다.

# ADR-0009. 추천 정확도를 측정하지 않기로 한 결정

- 상태: Accepted
- 날짜: 2026-09
- 프로젝트: Illo-on

## 맥락

"추천 모델 정확도(Recall@K, NDCG)를 내놓으라"는 요구가 자연스럽게 나온다.
포트폴리오에 숫자가 하나 더 붙으니 유혹도 있다.

## 왜 성립하지 않는가

행동 로그는 `user_event_generator.py` 가 만든다. 규칙이 상수로 박혀 있다.

```python
match_score = round(random.uniform(0.65, 0.98), 2) if is_ai else None
view_count  = random.randint(20, 250) if is_ai else random.randint(5, 150)

bookmark_p = 0.20 if is_ai else 0.12
if random.random() < bookmark_p:
    ...
    apply_p = 0.35 if is_ai else 0.20
    if random.random() < apply_p:
```

원본 로그로 확인한 값:

| | 조회 | 북마크 | 지원 |
|---|---|---|---|
| AI 추천 | 110,333 | 22,039 (**20.0%**) | 7,668 (조회 대비 **6.95%**) |
| 일반 | 91,465 | 11,123 (12.2%) | 2,211 (2.42%) |

설계값(0.20, 0.20×0.35=7.0%)과 소수점까지 맞는다.
**"AI 추천이 더 잘 먹힌다"는 결론은 발견이 아니라 설정이다.**

이 로그로 추천 모델을 평가하면 상수 0.35/0.20 을 얼마나 잘 복원했는지를 재는 것이 된다.
순환 논리다. "Recall@10 = 0.82" 같은 숫자를 내놓으면 로그 생성 방식을 묻는 순간
그 숫자뿐 아니라 다른 수치의 신뢰까지 깎인다.

`analyze_job_popularity.py` 의 GBTRegressor 도 같다. 학습 타깃인 조회수·지원수가
`is_ai` 로만 갈리는 uniform random 이라 R² 를 내놓아도 의미가 없다.

## 이미 드러난 증거 — `analysis_4`

"AI 매칭 점수 구간별 지원 전환율" 분석의 실제 출력:

| score_bucket | 0.6~0.7 | 0.7~0.8 | 0.8~0.9 | 0.9~1.0 |
|---|---|---|---|---|
| 지원전환율 | 10.5% | 10.7% | 10.9% | 10.6% |

**평평하다.** 그럴 수밖에 없다 — `match_score` 는 `random.uniform(0.65, 0.98)` 로
공고마다 한 번 뽑히고 `apply_p` 와 아무 관계가 없다.
이 분석은 구조적으로 아무것도 측정하지 못한다.

(덧붙여 이 10.6% 자체도 부정확하다. 조회와 지원을 잇는 키가 이벤트에 없어
`(user_id, job_id)` 로 조인하는데 같은 사용자가 같은 공고를 평균 1.30회 보므로
팬아웃이 생긴다. 설계상 참값은 6.95%다.)

## 결정

**추천 정확도와 인기도 모델 성능을 측정하지 않는다.** 대신 이 문서를 남긴다.

측정할 수 있는데 안 한 것이 아니라, **이 데이터 구조에서는 측정이 성립하지 않는다**는
판단이다. 평가를 생략한 것과 평가 가능 조건을 아는 것은 다르다.

## 무엇이 갖춰지면 측정할 수 있나

1. 실사용 행동 로그, 또는 최소한 사람이 만든 정답 셋
2. 조회–지원을 잇는 키(`view_id`) — 현재 스키마에는 없다
3. 추천 노출 로그 — 무엇을 보여줬는지가 없으면 CTR 계열 지표를 못 만든다

검색 품질은 사정이 다르다. 공고에 직군 라벨이 붙어 있어 정답이 데이터에 이미 있고,
시뮬레이터가 만든 것이 아니다. 그래서 검색은 측정했다 (README "검색 품질" 절).
